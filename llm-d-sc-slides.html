Background

Why Semantic Routing?

For LLM-backed applications and developer workflows

  • Not all requests are created equal; matching each request to the model capacity it needs can reduce costs.
    • i.e. "Let's implement this next feature in Rust" vs "Remind me the git command to undo my last commit"
  • Requests containing personal or organizational data may need to stay on-premises for security and privacy concerns.
    • "Sure. My social security number is..."
  • Domain-specific requests can be routed to specialized models for more relevant responses.

Component overview

llm-d-sc: Semantic classification
for inference routing

A classifier the gateway consults on every request.

How it works

  • Receives the prompt over gRPC
  • Compares against labelled example requests (anchor)
  • Returns one label: SIMPLE, MEDIUM, COMPLEX or REASONING

How it runs

  • Runs entirely on CPU and is written in Rust.
  • Designed for lightweight, low-latency classification
  • Rejects excess requests rather than queueing them

Limitations

Known gaps in this routing path

Component limits and their consequences in this CPU/GPU routing path.

Conversation continuity

  • The Praxis filter is designed to send just the latest user message to llm-d-sc.
  • But a long GPU session routed to the CPU can hit a cold KV cache.

Classification confidence

  • Scores rank labels but are not calibrated probabilities.
  • No fallback for uncertain classifications.

Health and metrics

  • No gRPC or HTTP readiness endpoint.
  • Timing data is logged, but no metrics endpoint is exposed.

Narrow Benchmarking

  • Published benchmarks come from one host.
  • Service round trips and pod CPU limits remain unmeasured upstream.
llm-d-sc supplies the label; the gateway chooses the model. sources: llm-d-sc README, specs/0.22-cache-session, docs/known-gaps.md
